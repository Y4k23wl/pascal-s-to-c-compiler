# 本地测试修复文档

本文档整理了本地 `testing/open_set/` 回归过程中发现并修复的问题。

## 1. 语言和文法覆盖不足

问题所在的测试文件：`testing/open_set/05_const_var_defn3.pas`、`testing/open_set/53_skip_spaces.pas`、`testing/open_set/19_if_test4.pas`、`testing/open_set/35_short_circuit3.pas`、`testing/open_set/46_full_conn.pas`、`testing/open_set/21_while_if_test2.pas`、`testing/open_set/58_many_params2.pas`、`testing/open_set/26_op_priority4.pas`、`testing/open_set/40_percolation.pas`、`testing/open_set/27_op_priority5.pas`、`testing/open_set/36_scope.pas`、`testing/open_set/45_dijkstra.pas`、`testing/open_set/64_nested_loops.pas`、`testing/open_set/29_unary_op2.pas`。

问题描述：本地开放测试集使用的语言形式超过了最初实现的 Pascal-S 子集，包括 `//` 行注释、带下划线的标识符、较长标识符、`while ... do` 循环、`true` / `false` 布尔字面量、零参数声明和调用、一元正号等。原实现没有完整覆盖这些形式，导致词法、语法或 AST 构造阶段失败。

负责模块：词法分析、语法分析与 AST 构造，部分规则联动语义分析。

解决方案：按开放测试集实际使用到的语言边界扩充词法规则和文法规则；为新增结构建立稳定的 AST 表示；在语义阶段为新增语句和表达式补充对应检查。扩充范围仅覆盖测试集实际要求的 Pascal-S 子集，不主动扩大到完整 Pascal。

最终是否解决：是

## 2. 零参数函数名作为表达式值

问题所在的测试文件：`testing/open_set/07_var_defn_func.pas`。

问题描述：零参数函数名直接作为表达式值使用时，原实现把它误判为非法变量引用，导致语义分析报错。

负责模块：语义分析。

解决方案：在表达式分析中区分变量引用与零参数函数取值。对于无参数函数，允许函数名在表达式位置代表其返回值；对于有参数函数，仍要求使用明确的函数调用形式。

最终是否解决：是

## 3. 函数调用语句返回值被忽略

问题所在的测试文件：`testing/open_set/66_matrix_add.pas`、`testing/open_set/43_exgcd.pas`。

问题描述：函数调用出现在语句位置且返回值未被使用时，原实现按照“语句位置只能调用过程”的规则报错，但开放测试集中允许这种写法。

负责模块：语义分析。

解决方案：放宽语句位置的调用检查，允许过程调用和函数调用都作为独立语句出现；函数调用语句只忽略返回值，参数数量、参数类型和 `var` 参数规则仍照常检查。

最终是否解决：是

## 4. 整数上的 `not` 运算

问题所在的测试文件：`testing/open_set/28_unary_op.pas`。

问题描述：测试集中存在 `not` 作用于整数表达式的情况，原语义规则只允许 `not boolean`，与测试集实际语义不一致。

负责模块：语义分析。

解决方案：按测试集语义扩展一元 `not` 的类型规则，使其同时支持布尔和整数操作数；语义分析根据操作数类型确定结果类型，代码生成阶段再选择对应的目标语言运算形式。

最终是否解决：是

## 5. 极长表达式导致语义分析崩溃

问题所在的测试文件：`testing/open_set/56_long_code2.pas`。

问题描述：该样例中存在极长加法链，原语义分析使用递归方式遍历表达式树，在深表达式上可能压爆 C++ 调用栈并崩溃。

负责模块：语义分析。

解决方案：将深表达式分析从递归遍历改为显式栈遍历，以后序方式计算子表达式和父表达式信息，使表达式深度不再受 C++ 调用栈限制。

最终是否解决：是


## 6. 函数实参求值顺序不确定

问题所在的测试文件：`testing/open_set/57_many_params.pas`。

问题描述：样例中包含大量带副作用的函数实参。原代码生成直接把这些实参交给 C 函数调用求值，而 C 语言函数实参求值顺序未指定，导致输出与 Pascal 参考程序不一致。

负责模块：目标代码生成。

解决方案：在实际调用前按参考语义固定实参求值顺序，并把每个实参结果保存到临时位置，再按原参数位置进行函数调用，避免把 Pascal 语义暴露给 C 的未指定求值行为。

最终是否解决：是
