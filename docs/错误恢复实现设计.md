# Pascal-S 错误恢复实现设计

## 1. 目标

本设计文档描述当前 Pascal-S 到 C 编译器中“错误恢复”能力的实现目标、分层策略、落地方式与测试方案。

这里的“错误恢复”不是指把错误程序修正成正确程序，而是指：

1. 编译器在遇到错误后尽量继续向后分析
2. 在一次编译中输出尽可能多且可信的错误信息
3. 避免因为第一处错误直接中断整次编译
4. 避免恢复过程本身导致死循环、崩溃或大面积伪错误

当前工程的主链路是：

```text
源程序
  -> Flex 词法分析
  -> Bison 语法分析 / AST 构造
  -> 语义分析
  -> C 代码生成
```

因此错误恢复也应按阶段设计，而不是只在某一层零散补丁式处理。

## 2. 设计边界

本项目的错误恢复目标是“课程设计级、可稳定演示、可支撑批量测试”的基本能力，不追求工业编译器那种复杂恢复。

本轮设计明确包含：

- 词法错误后的继续扫描
- 语法错误后的同步点恢复
- 语义错误的累计报告
- 错误数量上限与噪声控制

本轮设计暂不包含：

- 自动插入或修改 token 的智能修复
- 基于编辑距离的纠错建议
- 错误节点参与后续代码生成
- IDE 级别的增量恢复

## 3. 当前实现现状

### 3.1 已有能力

- 词法层已能报告非法字符、非法标识符、未闭合字符常量、未闭合注释
- 大部分局部词法错误在报错后会继续扫描
- 语义分析已使用 `Invalid` 类型来避免单点语义错误打断整个分析
- 语义错误可以累计保存到 `SemanticResult.errors`

### 3.2 当前缺失

- 语法层没有 `error` 产生式
- 没有按 `;`、`end`、`)` 等同步符号恢复
- 语法错误基本仍是“报第一条后结束解析”
- 未设置错误数量上限
- 没有专门的错误恢复测试样例

## 4. 总体策略

建议采用“三层恢复、逐层保守”的策略：

### 4.1 词法层

目标：

- 尽量把坏字符或坏词法单元局部吞掉
- 保持后续 token 流仍可被语法器消费

原则：

- 能局部跳过的就跳过
- 无法继续形成稳定 token 流时再终止

### 4.2 语法层

目标：

- 在关键结构边界上恢复
- 继续构造“尽量可信”的后续 AST
- 报告多条语法错误

原则：

- 只在低风险同步点恢复
- 恢复规则优先覆盖高频错误位置
- 不做复杂猜测，只做边界跳转

### 4.3 语义层

目标：

- 对合法 AST 子树继续做检查
- 利用 `Invalid` 类型抑制连锁报错

原则：

- 一条语义错误不影响后续无关节点
- 同一根因不重复刷屏

## 5. 词法恢复设计

词法层对应文件：

- `code/frontend/pascal_s_lexer.l`

### 5.1 保留现有做法

以下错误继续保持“报错后前进”：

- 非法字符
- 数字开头标识符
- 未闭合字符常量

这类错误的共同特点是：

- 错误局部明确
- 跳过当前坏片段后，后续输入边界仍清晰

### 5.2 需要补强的点

#### 未闭合注释

当前未闭合注释会直接 `return 0`，等价于提前结束整个输入流。

建议改进为：

- 报错后设置词法失败标记
- 仍返回 EOF 给语法器
- 驱动层按“词法失败”输出阶段性错误

这里不建议强行继续扫描注释后的内容，因为注释本身已经吞掉了后续边界，继续恢复的可信度很低。

#### 错误计数

建议在词法层维护：

```cpp
static int g_lex_error_count = 0;
static const int kMaxLexErrors = 20;
```

达到上限后：

- 输出“词法错误过多，停止扫描”
- 返回 EOF

这样可以避免恶意或极差输入导致刷屏。

## 6. 语法恢复设计

语法层对应文件：

- `code/frontend/pascal_s_parser.y`

语法恢复是本次设计的重点。

### 6.1 恢复目标

至少支持以下高频场景：

- 语句后缺失分号
- 复合语句内部某条语句损坏
- 形参列表中局部出错
- `read(...)` / `write(...)` / 调用实参列表中局部出错
- 缺右括号、右中括号
- 子程序体内部局部语法错误后继续处理后续语句

### 6.2 同步点选择

基本同步符号建议为：

- `SEMICOLON`
- `END_KW`
- `RPAREN`
- `RBRACK`
- `DOT`

原因：

- 它们本身就是 Pascal 结构边界
- 跳到这些符号处恢复，误吞后续合法结构的风险较低

### 6.3 恢复规则放置位置

不建议一开始就在所有非终结符里都加 `error` 规则。  
更稳妥的做法是优先在以下“边界层”加入恢复：

#### `statement_list`

这是最关键的恢复点。建议增加：

```bison
statement_list
    : statement
    | statement_list SEMICOLON statement
    | statement_list SEMICOLON error
      {
          yyerror("语句存在语法错误，已跳过到下一个分号后继续");
          yyerrok;
          $$ = $1;
      }
```

作用：

- 当某条语句损坏时，跳过到下一个分号
- 不丢掉前面已经构造好的语句列表

#### `compound_statement`

建议增加：

```bison
compound_statement
    : BEGIN_KW statement_list END_KW
    | BEGIN_KW error END_KW
      {
          yyerror("复合语句内部存在语法错误，已恢复到 end");
          yyerrok;
          $$ = ast_make_compound_stmt(ast_new(AST_STATEMENT_LIST, AST_LOC(@$)), AST_LOC(@$));
      }
```

作用：

- 当整个 `begin ... end` 内部损坏严重时，直接同步到 `end`

#### `formal_parameter`

建议增加：

```bison
formal_parameter
    : LPAREN parameter_list RPAREN
    | LPAREN error RPAREN
      {
          yyerror("形参列表存在语法错误，已恢复到右括号");
          yyerrok;
          $$ = ast_new(AST_PARAM_LIST, AST_LOC(@$));
      }
```

#### `procedure_call` / `factor` 中的实参列表

建议增加：

```bison
procedure_call
    : ID LPAREN error RPAREN
      {
          yyerror("调用实参列表存在语法错误，已恢复到右括号");
          yyerrok;
          $$ = ast_make_call(AST_CALL_STMT, $1, ast_new(AST_EXPRESSION_LIST, AST_LOC(@$)), AST_LOC(@$));
          free($1);
      }
```

表达式形式调用同理。

### 6.4 AST 构造策略

恢复后 AST 不要求“完全正确”，但要满足两个条件：

1. 结构上不崩
2. 后续语义分析可以识别出“这是残缺节点”并选择跳过

因此建议：

- 语句列表恢复时尽量保留已成功构造的旧节点
- 无法构造的当前位置补成 `AST_EMPTY_STMT`
- 参数列表/实参列表恢复时可返回空列表节点，而不是 `NULL`

这样可以减少后续大量空指针分支。

### 6.5 `yyerror()` 行为调整

当前 `yyerror()` 只做简单报错。建议改成：

- 统计语法错误数
- 区分“普通语法错”和“恢复提示”
- 达到上限后终止解析

建议增加：

```cpp
static int g_parse_error_count = 0;
static const int kMaxParseErrors = 20;
```

策略：

- 每次进入 `yyerror()` 时递增计数
- 超过上限后直接停止解析

### 6.6 噪声控制

语法恢复最容易产生“连锁报错”。为降低噪声，建议：

- 同一个恢复分支里不要重复调用多次 `yyerror()`
- 对 `error` 规则命中的情况使用简短、固定格式的恢复提示
- 恢复后依赖 `yyerrok` 清掉当前错误状态

不建议在第一版实现里大量使用 `yyclearin`，除非明确需要丢弃一个 lookahead token，否则会让行为更难预测。

## 7. 语义恢复设计

语义层对应文件：

- `code/semantic/semantic.hpp`
- `code/semantic/semantic.cpp`

### 7.1 保持 `Invalid` 类型作为核心恢复手段

当前 `Invalid` 类型设计是正确的，应继续保留。

建议保持以下规则：

- 某个表达式一旦推导为 `Invalid`
- 后续依赖它的检查尽量少报或不重复报
- 但与其无关的兄弟节点仍继续分析

### 7.2 针对恢复 AST 的兼容

引入语法恢复后，语义阶段需要面对更多“占位节点”：

- 空表达式列表
- 空参数列表
- 空语句
- 被恢复规则截断的局部结构

因此语义分析要补一条原则：

- 对空列表节点视为合法空结构
- 对恢复产生的缺失子节点，优先返回 `Invalid`
- 不要因为局部缺子节点而 `assert` 失败

### 7.3 连锁错误抑制

建议新增两个简单策略：

#### 未声明标识符只报一次

同一节点命中的同一根因，不重复上报。

#### 类型已无效时停止深究

例如：

- 左值已经是 `Invalid`
- 就不要再继续报“赋值类型不兼容”

这部分当前已有一定基础，但在引入语法恢复后需要更严格执行。

## 8. 驱动层设计

驱动层对应文件：

- `code/pascal_s_driver.cpp`

### 8.1 阶段失败判定

建议区分三类失败：

1. 词法失败
2. 语法失败
3. 语义失败

输出时明确标明阶段，不把所有问题都混成“parse error”。

### 8.2 是否继续生成 C

恢复的目标是“多报错”，不是“带错生成代码”。  
因此规则应明确：

- 只要词法或语法阶段失败，就不进入代码生成
- 只要语义阶段失败，就不生成 C

也就是说，错误恢复只服务于诊断能力，不改变“错误程序不能生成目标代码”的总原则。

## 9. 实现顺序

建议按最小可用版本分三步做。

### 第一步：最小语法恢复

目标：

- 在 `statement_list`
- `compound_statement`
- `formal_parameter`
- 调用实参列表

这四类位置加入 `error` 产生式。

预期收益：

- 一份程序里能稳定输出多条语法错误
- 最常见的缺分号、坏语句、坏参数列表都能恢复

### 第二步：错误计数与上限

目标：

- 词法错误上限
- 语法错误上限
- 超限后停止并给出总结提示

预期收益：

- 避免噪声爆炸
- 恢复行为更可控

### 第三步：语义层兼容恢复 AST

目标：

- 补齐空列表、占位节点、`Invalid` 分支的稳健处理

预期收益：

- 语法恢复后不会把语义阶段打崩
- 语义错误报告仍然可用

## 10. 测试设计

错误恢复必须用“错误输入”专门验证，不能只跑 `open_set`。

建议新增 `testing/error_recovery/`，至少包含以下样例。

### 10.1 语句级恢复

- 缺少分号后继续下一条语句
- 赋值语句右侧表达式损坏
- `if` 的条件表达式损坏但后续语句仍能继续

### 10.2 结构级恢复

- `begin ... end` 内部某条语句损坏
- 形参列表中间缺 `:`
- 调用实参列表中间缺逗号或表达式

### 10.3 词法级恢复

- 非法字符后继续
- 坏字符常量后继续
- 连续多个词法错误时上限控制

### 10.4 噪声控制

- 单个根因不应触发十几条连锁错误
- 恢复后不应死循环
- 错误条数应稳定

## 11. 验收标准

若实现“基本错误恢复”，建议验收标准定为：

1. 一份包含多处错误的程序，至少能稳定报告 3 条以上错误
2. 缺分号、坏语句、坏参数列表可以恢复到后续结构
3. 编译器对错误输入不崩溃
4. 错误过多时能停止而不刷屏
5. 恢复后不会继续生成 C 代码

## 12. 风险与取舍

### 12.1 风险

- `error` 规则加得太多会制造 shift/reduce 冲突
- 恢复点选得太激进会吞掉本来正确的后续结构
- AST 占位节点过多会让语义阶段复杂化

### 12.2 取舍

因此本项目应坚持：

- 先做少量高价值恢复点
- 先保证稳定，再追求更多错误数
- 先保证不崩，再提升错误信息质量

## 13. 最小结论

对当前项目来说，最小且值得实现的错误恢复方案是：

1. 词法层保留现有“局部跳过”策略，并加入错误上限
2. Bison 在语句列表、复合语句、参数列表、调用实参列表加入 `error` 产生式
3. 语义层继续依赖 `Invalid` 类型累计错误
4. 驱动层明确“恢复仅用于诊断，不用于带错生成代码”

做到这一步，就可以把当前编译器从“遇到第一条语法错基本就停”的状态，提升到“能在一次编译里稳定报告多条可信错误”的课程设计级实现。
