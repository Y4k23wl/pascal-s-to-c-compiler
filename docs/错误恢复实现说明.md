# Pascal-S 错误恢复实现说明

## 1. 实现目标

本次实现按照“课程设计级、保守恢复”的原则落地错误恢复：

1. 一次编译尽量继续向后分析并报告多条错误
2. 恢复范围只放在边界清晰的位置
3. 有错误时仍然禁止进入代码生成
4. 避免恢复本身制造大量伪错误或崩溃

对应参考设计文档：

- `docs/错误恢复实现设计.md`

## 2. 实现分阶段

### 2.1 第一阶段：基础语法恢复

优先实现了高价值、低风险的恢复点：

- `statement_list`
  - 增加“语句之间可能缺少分号”的恢复规则
  - 增加“当前语句损坏，跳过到下一个分号或 `end`”的恢复规则
- `compound_statement`
  - 增加 `begin ... end` 的结构级兜底恢复
- `formal_parameter`
  - 形参列表出错时同步到 `)`
- `procedure_call` / `factor`
  - 过程/函数调用实参列表出错时同步到 `)`
- `READ` / `WRITE`
  - 输入输出参数列表出错时同步到 `)`
- `id_varpart`
  - 数组下标列表出错时同步到 `]`

恢复动作的 AST 策略如下：

- 坏语句直接丢弃，不破坏已有 `statement_list`
- 形参列表恢复为 `AST_PARAM_LIST`
- 实参列表恢复为 `AST_EXPRESSION_LIST`
- `read` 恢复为空 `AST_VARIABLE_LIST`
- 复合语句兜底恢复为空 `AST_STATEMENT_LIST`

这样做的原因是：

- 不新增 AST kind，和现有语义/代码生成接口兼容
- `ast_validate()` 仍能通过
- 恢复后节点结构稳定，不依赖大量额外空指针判断

### 2.2 第二阶段：错误计数与停止条件

在词法和语法两层都加入了错误数量上限：

- 词法：`kMaxLexErrors = 20`
- 语法：`kMaxParseErrors = 20`

行为约定：

- 每次报错时累计计数
- 达到上限后输出“错误过多，停止分析”
- 词法层返回 EOF 停止扫描
- 语法层通过全局停止标记通知词法器不再继续取 token

此外，未闭合注释会被视为“词法提前终止”：

- 先报告词法错误
- 直接结束扫描
- 抑制由截断输入额外诱发的伪语法错误

### 2.3 第三阶段：驱动与阶段判定

前端接口新增了阶段状态查询函数：

- `pascal_s_had_lexical_error()`
- `pascal_s_lexical_error_count()`
- `pascal_s_had_syntax_error()`
- `pascal_s_syntax_error_count()`

驱动层据此补充了阶段性总结：

- 词法阶段错误汇总
- 语法阶段错误汇总
- 语义阶段错误汇总

并保持原有总原则不变：

- 词法或语法阶段只要出错，就不进入语义后续生成链路
- 语义阶段出错，也不生成 C

## 3. 关键实现细节

### 3.1 `statement_list` 的取舍

本项目最常见、最值得恢复的错误是语句边界问题，因此主恢复点放在 `statement_list`。

当前采用了两条规则：

- `statement_list error statement`
  - 用于“缺少分号后直接开始下一条语句”
  - action 里调 `yyerrok` 清错误状态，让后续语句正常计入
- `statement_list SEMICOLON error`
  - 用于“分号后当前语句本身损坏，跳过到下一同步点”
  - action 里**不**调 `yyerrok`，让 Bison 默认的"出错后静默丢弃
    token 直到 3 个成功 shift"抑制机制接管，避免恢复后立刻在同一
    位置重报死循环（详见 §8 修复说明）

这两条规则和 Pascal-S 的“空语句”会引入 2 个受控的 `shift/reduce` 冲突。  
为避免误判，语法文件中显式使用了 `%expect 2` 固定该行为。

实际选择是优先走恢复分支，这比简单把它们删掉更符合本项目的展示目标。

### 3.2 为什么不用复杂错误节点

课程设计里不需要工业级恢复。若引入额外 `AST_ERROR_*` 节点，会带来：

- AST 校验逻辑修改
- 语义分析额外分支
- 代码生成额外分支
- 文档和测试范围同步扩大

因此本次实现坚持复用现有节点：

- 空语句
- 空列表
- 已成功构造的前序节点

### 3.3 为什么不带错生成 C

错误恢复的目的是“多报错”，不是“修程序”。  
恢复后的 AST 只保证结构稳定，不保证语义可信，因此：

- 前端出错后统一返回 `nullptr`
- 驱动层停止后续生成

这可以避免课程设计演示时出现“明明前面报了一堆错，后面还生成一份看似正常的 C”的歧义。

### 5.3 金标准与回归

每个 `.pas` 旁会有同名的 `*.expected.stderr` 和 `*.expected.exit`，
分别是编译器当前期望写入 stderr 的完整内容与期望退出码。脚本会逐字节
diff stderr 并对比退出码，任一不一致即报 `STDERR_MISMATCH` / `EXIT_MISMATCH`。

回归命令（任一即可）：

```bash
./testing/run_error_recovery_checks.sh
python3 testing/run_tests.py error-recovery
```

当前共 18 个样例，均通过。

## 6. 当前能力边界

本次实现故意没有做以下内容：

- 自动补 token
- 智能拼写纠正
- 表达式内部复杂猜测恢复
- 带错继续生成目标代码

这不是缺陷，而是和课程设计目标一致的边界控制。

## 7. 实测现象总结

当前版本已经可以稳定做到：

1. 一份程序内连续报告多条语法错误
2. 在缺分号、坏参数列表、坏下标列表场景下继续向后分析
3. 词法错误过多时停止刷屏
4. 未闭合注释时只报词法阶段错误，不再额外制造伪语法错误
5. 正确程序编译链路不受影响

## 8. 配套修复的两个错误处理缺陷

错误恢复测试集扩充过程中暴露并修复了两个真实缺陷，对应改动已合入主代码
并被相应回归样例锁住。

### 8.1 纯词法错误不致命

**现象**：对于 `123abc` 这类非法标识符，词法器丢弃 token 后 parser 仍能
完成一棵 AST，`root != NULL`，于是 `pascal_s_driver.cpp` 跳过词法错误
检查直接走 semantic → codegen，最终 exit=0。stderr 里能看到 `[词法错误]`
却没有 "编译终止" 汇总条，与设计目标"词法或语法阶段失败就不进入代码生成"
矛盾。

**修复**：`code/pascal_s_driver.cpp` 把 `pascal_s_had_lexical_error()`
检查从 `if (root == NULL)` 分支里提出来，发现词法错误就直接打汇总条并
`return 1`。

**锁住**：`testing/error_recovery/10_bad_identifier_digit_start.pas`、
`11_lex_below_threshold.pas`（`expected.exit = 1`，golden stderr 含
汇总条）。

### 8.2 `statement_list` 错误恢复死循环

**现象**：`statement_list SEMICOLON error` 规则的 action 里调了
`yyerrok`，会清掉 Bison 自带的"出错后静默丢弃 token 直到 3 个成功 shift"
抑制机制。当坏 token 在恢复 reduce 之后**仍然处于 lookahead 位置**，
parser 立刻在同一位置重报 → 同一条规则再触发 → 死循环。`kMaxParseErrors`
只抑制新错的打印，但恢复注释不受其约束，最终能产生约 137 MB stderr。

**修复**：`code/frontend/pascal_s_parser.y` 去掉 `statement_list
SEMICOLON error` 规则里的 `yyerrok`，让 Bison 默认抑制接管，循环
自然终止。注意：另一条 `statement_list error statement` 规则的
`yyerrok` 保留不动，01 样例依赖它继续把恢复后的后续语句串起来。

**锁住**：`testing/error_recovery/13_loop_recovery_regression.pas`
——同一份输入在修复前是死循环，现在干净地报 3 条错误并 exit=1。

### 8.3 与设计文档的关系

`错误恢复实现设计.md` §6.6 原文建议"恢复后依赖 `yyerrok` 清掉当前
错误状态"。这条建议在 `statement_list error statement` 上正确，
但放到 `statement_list SEMICOLON error` 上会触发 §8.2 的循环；
设计文档已在对应章节加补充说明。
