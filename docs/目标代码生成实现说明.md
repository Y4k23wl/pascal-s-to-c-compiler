# Pascal-S 目标代码生成实现说明

本文档描述当前工程中目标代码生成模块的实际实现，对应代码文件为：

- `code/codegen.hpp`
- `code/codegen.cpp`
- `code/pascal_s_driver.cpp`

这部分实现直接消费 `SemanticAnalyzer` 产出的 `SemanticResult`，不再重新做名字解析和类型推导。也就是说，代码生成阶段默认前提是：

1. AST 已通过 `ast_validate()`
2. `SemanticResult.ok == true`
3. `resolved_symbols / expr_info / function_result_refs / Symbol.c_name` 都已经可用

## 1. 对外接口

`codegen.hpp` 暴露的唯一入口是：

```cpp
class CodeGenerator {
public:
    std::string generate(const AstNode *root, const SemanticResult &sem);
};
```

调用方式已经接入 `pascal_s_driver.cpp`：

1. 先解析 Pascal-S 源程序
2. 再做 AST 校验
3. 再做语义分析
4. 语义通过后调用 `CodeGenerator::generate()`
5. 通过 `-i source.pas` 推导输出路径，并把生成出的完整 C 源码写到同目录同名 `.c` 文件

驱动里 `--dump-ast` 仍然保留，但 AST 改为输出到 `stderr`，这样不会污染生成的 C 代码。

## 2. 生成器内部状态

`CodeGenerator` 不是无状态函数集合，而是一个带上下文的发射器。`reset()` 会初始化以下状态：

- `out_`
  - 最终输出缓冲区，类型为 `std::ostringstream`
- `sem_`
  - 指向当前轮代码生成使用的 `SemanticResult`
- `indent_level_`
  - 当前缩进层级
- `for_temp_counter_`
  - 为 `for` 终值缓存变量生成唯一名字，例如 `__for_end_1`
- `call_temp_capacity_` / `call_temp_usage_`
  - 为带实参调用预分配并顺序复用临时槽
- `owner_scopes_`
  - `AstNode* -> Scope*` 的映射

`owner_scopes_` 的建立方式是遍历 `sem.scope_storage`。这样代码生成阶段就能从 AST 节点回到语义阶段已经建好的作用域，例如：

- `AST_PROGRAM` 对应全局作用域
- `AST_SUBPROGRAM` 对应子程序局部作用域

这一步的作用很直接：生成声明语句时，不需要重新扫描符号表层次，只要拿当前 AST 所属作用域按名字查符号即可。

## 3. 顶层输出结构

`emit_program()` 决定整个 C 文件的骨架，顺序固定为：

1. `#include`
2. 运行时辅助函数
3. 调用实参临时槽声明
4. 全局常量与变量声明
5. 子程序原型
6. 子程序定义
7. `main`

具体代码路径如下：

- `emit_helpers()`
  - 生成 `write_real()`、`read_bool()` 和 `write_bool()`
- `emit_call_temp_decls()`
  - 生成 `__call_tmp_*` 临时槽数组，用来固定实参求值顺序
- `emit_global_decls()`
  - 读取主程序 `AST_BLOCK` 的常量/变量声明并发射到文件作用域
- `emit_prototypes()`
  - 先输出所有过程/函数原型，避免“先用后定义”问题
- `emit_subprograms()`
  - 输出所有过程/函数定义
- `emit_main()`
  - 把 Pascal 主程序体翻译成 `int main(void)`

这里和旧驱动最大的区别是：主程序块里的 `var` 声明不会再被塞进 `main`，而是全部放在文件作用域。这样 C 中的函数定义也能直接访问 Pascal 主程序层定义的全局变量。

## 4. 声明生成

### 4.1 符号来源

代码生成阶段不自己发明名字，而是统一复用语义分析阶段的 `Symbol.c_name`。

声明生成的查找方式有两种：

- `lookup_global_symbol()`
  - 从 `sem.global_scope` 取全局符号，主要用于过程/函数头
- `lookup_symbol(scope, name)`
  - 从指定作用域拿常量、变量、参数

这样生成器天然继承了语义阶段已经确定好的命名规则：

- 全局变量 `g_`
- 局部变量 `l_`
- 参数 `p_`
- 常量 `c_`
- 子程序 `fn_`

### 4.2 常量与变量

`emit_const_decls()` 和 `emit_var_decls()` 分别处理 `AST_CONST_DECL_LIST`、`AST_VAR_DECL_LIST`。

实现细节是：

- 常量声明：
  - 根据声明名在当前作用域查 `Symbol`
  - 再对 `children[0]` 的常量值节点调用 `emit_expr()`
  - 生成 `const <type> <c_name> = <expr>;`
- 变量声明：
  - 遍历声明里的每个标识符
  - 为每个变量单独输出一行声明，方便调试

真正拼接 C 声明文本的是 `emit_decl()`。它按三种情况分支：

1. 普通标量
2. `var` 参数映射后的指针
3. Pascal 数组映射成的 C 数组

例如：

- `integer x` -> `int16_t g_x;`
- `var y: integer` -> `int16_t *p_y`
- `array[1..3, 0..5] of integer a` -> `int16_t g_a[3][6];`

这里后来做过一次和端到端对拍直接相关的修正：

- 已声明为 `integer` 的变量、数组元素、参数、函数返回值，按当前 FPC 参考行为映射成 16 位有符号整数
- 无显式类型的整型常量声明，例如 `const modn = 1000000007;`，仍保留为 `const int`

这样 `42_color.pas` 这类依赖 16 位截断的样例能与 Pascal 参考输出一致，同时不会把大整数字面量常量在声明阶段错误截断。

Pascal `real` 现在统一映射成 C `double`，所以：

- `real x` -> `double g_x;`
- `function f(...): real` -> `double fn_f(...)`

这一步是从早期的 `float` 调整过来的，目的是对齐 `write(real)` 的精度和运行结果。

数组长度由 `ArrayBound.high - ArrayBound.low + 1` 计算，直接来自 `SemType.bounds`。

### 4.3 函数/过程签名

`emit_signature()` 根据 `Symbol` 生成 C 函数签名。

关键点有两个：

- 过程的返回类型来自 `SemType::Void`，映射成 `void`
- 零参数过程/函数生成成 `(void)`，而不是空参数表 `()`

参数生成时没有再读 AST，而是直接遍历 `Symbol.params`。这是因为参数的 `by_ref`、类型和 `c_name` 都已经在语义分析阶段固定好了。

## 5. 子程序体生成

### 5.1 入口

`emit_subprogram()` 负责单个 `AST_SUBPROGRAM` 的定义。

处理顺序是：

1. 用头部名字在全局作用域取到过程/函数符号
2. 用 `scope_for_owner(subprogram)` 找到该子程序的局部作用域
3. 输出函数签名
4. 若是函数，先声明隐藏返回变量 `__result`
5. 输出局部常量、局部变量
6. 输出语句
7. 若是函数，最后 `return __result;`

### 5.2 函数返回值

Pascal 函数不是 `return expr`，而是对函数名赋值。这个语义在代码生成里通过 `__result` 落地：

- 语义分析阶段已经把“函数结果赋值”的左值节点放进 `SemanticResult.function_result_refs`
- 代码生成阶段 `emit_assignment_target()` 会先检查该集合
- 命中时直接把赋值左侧发射为 `__result`

因此：

```pascal
plusone := n + 1
```

会在 C 中生成：

```c
__result = p_n + 1;
```

而不是把 `plusone` 当普通变量处理。

`emit_default_value()` 负责函数入口处 `__result` 的默认初始化，当前规则为：

- `integer` -> `0`
- `real` -> `0.0`
- `boolean` -> `false`
- `char` -> `'\0'`

## 6. 表达式生成

### 6.1 基本分工

表达式主入口是 `emit_expr()`，实际工作由 `emit_expr_with_parent()` 完成。

这样拆分的原因是：代码生成后期发现 `56_long_code2.pas` 这类超长表达式如果“每一层都强制套括号”，会让生成的 C 在编译时触发括号深度上限。因此现在的实现改成了：

- `expr_precedence()`
  - 返回当前 AST 表达式节点在 C 中对应的优先级层次
- `emit_expr_with_parent(node, parent_precedence, is_right_child)`
  - 只在必要时补括号

当前策略是：

- 若子表达式优先级低于父节点，必须加括号
- 若子表达式是“同优先级的右孩子”，也保守加括号
- 左结合链上的左孩子尽量不加括号

这样既保住语义，也能把：

```text
(((a + b) + c) + d)
```

压平成：

```c
a + b + c + d
```

避免生成器把长表达式变成“括号塔”。

### 6.2 变量引用与函数调用

`emit_var_ref()` 直接依赖 `resolved_symbols[node]`。

它处理了三类特殊情况：

1. 普通变量
   - 直接输出 `symbol.c_name`
2. `var` 标量参数
   - 作为表达式使用时输出 `(*p_x)`
3. 零参数函数名直接作为表达式
   - 语义分析会把它解析成 `Function` 符号
   - 这里直接输出 `fn_name()`

如果变量带下标，数组访问的核心逻辑也在 `emit_var_ref()`：

- 先拿符号上的 `SemType.bounds`
- 再把每一维下标发射成 `(<expr>) - low`
- 最终拼成 `a[idx1][idx2]...`

所以 Pascal：

```pascal
a[i, j]
```

在下界分别为 `1`、`0` 时会生成：

```c
g_a[(i) - 1][(j)]
```

### 6.3 调用实参

`emit_call()` 统一处理过程调用和函数调用。

这里后来专门为 `57_many_params.pas` 做过修正。最早的实现是把实参表达式直接拼进 C 调用点，但这会把 Pascal 的实参求值语义直接暴露给 C，而 C 的参数求值顺序本身未指定。

当前实现改成两步：

1. 先把每个实参求值到 `__call_tmp_*` 临时槽
2. 再用这些临时槽按原参数顺序发出真正的调用

为了对齐当前 FPC 参考行为，实参求值顺序显式固定为“从右到左求值，但按原参数位置传入”。生成形态类似：

```c
(__call_tmp_i[1] = expr2,
 __call_tmp_i[0] = expr1,
 fn(__call_tmp_i[0], __call_tmp_i[1]))
```

其中：

- 值参数使用值临时槽
- `var` 参数使用指针临时槽

`emit_address_of()` 则负责把语义上已验证为左值的 `var` 实参统一生成：

```c
&(<expr>)
```

它能同时覆盖：

- 普通变量 `&(g_x)`
- 数组元素 `&(g_a[(i) - 1])`
- 引用参数自身 `&((*p_x))`

最后一种虽然看起来多了一层形式上的 `&*`，但在 C 中是合法且等价的。

### 6.4 一元与二元运算

实现位于 `emit_expr_with_parent()`。

二元运算映射规则是：

- `=` -> `==`
- `<>` -> `!=`
- `div` -> `/`
- `mod` -> `%`
- `and` -> `&&`
- `or` -> `||`

对应代码在 `binary_op_to_c()`。

有两个额外细节：

1. Pascal `/` 固定是实数除法
   - 如果两边在语义信息里都是 `integer`
   - 生成器会显式输出 `(double)` 转换
2. Pascal `not` 在语义阶段允许作用于 `boolean` 和 `integer`
   - `boolean` 生成 `!expr`
   - `integer` 生成 `~expr`

第二点不能简单统一成 `!`，否则整数 `not` 会被错误地编译成逻辑非。

## 7. 语句生成

### 7.1 基本入口

`emit_stmt()` 负责分发所有语句节点，当前覆盖：

- `AST_COMPOUND_STMT`
- `AST_EMPTY_STMT`
- `AST_ASSIGN_STMT`
- `AST_CALL_STMT`
- `AST_IF_STMT`
- `AST_WHILE_STMT`
- `AST_FOR_STMT`
- `AST_READ_STMT`
- `AST_WRITE_STMT`

`emit_stmt_as_block()` 用来保证 `if`、`while`、`for` 的子语句始终落在花括号块里，不会因为 Pascal 源代码没写 `begin ... end` 就在生成的 C 里出现悬挂结构。

### 7.2 赋值

赋值语句的生成逻辑很简单，但依赖语义结果：

- 左侧由 `emit_assignment_target()` 生成
- 右侧由 `emit_expr()` 生成

其中 `emit_assignment_target()` 的唯一特殊分支就是函数结果赋值：

- 如果节点在 `function_result_refs` 里
- 直接输出 `__result`

### 7.3 `for`

`emit_stmt()` 里的 `AST_FOR_STMT` 分支专门实现了 Pascal `for ... to ... do` 的“终值只求一次”语义。

它会生成如下结构：

```c
{
    int __for_end_1 = <finish>;
    for (loop_var = <start>; loop_var <= __for_end_1; ++loop_var) {
        ...
    }
}
```

这里循环变量不是从 AST 文本直接拼，而是从 `resolved_symbols[node]` 拿符号后再转成：

- 普通变量 -> `g_i` / `l_i`
- 引用参数 -> `(*p_i)`

这样即使 `for` 目标是 `var` 参数，也不会在代码生成阶段丢失语义。

### 7.4 `read` / `write`

`read` 和 `write` 都按“逐项发射”实现，不拼多参数格式串。

`read` 的实现位于 `AST_READ_STMT` 分支：

- `integer` -> `scanf("%hd", &x);`
- `real` -> `scanf("%lf", &x);`
- `char` -> `scanf(" %c", &x);`
- `boolean` -> `read_bool(&x);`

`write` 的实现位于 `AST_WRITE_STMT` 分支：

- `integer` -> `printf("%d", (int)expr);`
- `real` -> `write_real(expr);`
- `char` -> `printf("%c", expr);`
- `boolean` -> `write_bool(expr);`

这里 `real` 输出也做过一次专门修正。最早直接用 `printf("%g", expr)`，虽然数值大体正确，但和参考 Pascal 编译器默认的 `write(real)` 格式不一致，典型问题包括：

- `14_div.pas` 中 `2.0` 被打印成 `2`
- `51_var_name.pas` 中多参数 `write` 丢失了实数前的空格
- `65_float.pas` 中精度明显不足

因此现在改成统一走 `write_real()`：

- 内部先按 `%.16E` 生成科学计数法
- 再把指数补成三位，例如 `E+000`、`E-001`
- 保留正数前导空格，以匹配 Pascal 默认的 `write(real)`

布尔 I/O 没有硬塞进 `scanf/printf` 格式串，而是和 `real` 一样交给辅助函数处理：

- `write_real()`
  - 输出与当前 FPC 默认 `write(real)` 兼容的科学计数法格式
- `read_bool()`
  - 当前接受 `true/false/1/0`
- `write_bool()`
  - 输出 `true` 或 `false`

## 8. 驱动程序集成

`pascal_s_driver.cpp` 现在的主流程是：

1. 解析命令行参数，要求支持 `-i source.pas`
2. 解析 Pascal-S 源程序
3. `ast_validate()`
4. `SemanticAnalyzer::analyze()`
5. 若有语义错误，打印错误并退出
6. `CodeGenerator::generate()`
7. 把生成的 C 代码写到输入文件同目录下的同名 `.c` 文件

也就是说，当前可执行文件已经从“语义检查器”升级成了符合课程评测接口的 Pascal-S 到 C 翻译器。

## 9. 本地验证

当前本地做了三层验证：

1. 用 `testing/open_set` 全部 70 个 `.pas` 批量生成 C 并用 `cc -std=c99` 编译
2. 用 Free Pascal Compiler 3.2.2 编译同一批 Pascal 源程序
3. 对每个样例运行“Pascal-S -> C -> 可执行文件”和“Pascal -> FPC -> 可执行文件”，逐一比对标准输出

对应自动化脚本是：

```bash
./testing/run_output_consistency.sh
```

修复 `write(real)`、`integer` 运行时表示和调用实参顺序后，`testing/open_set` 当前已达到 `70/70` 端到端输出一致。
