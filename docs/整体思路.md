# Pascal-S 到 C 编译器实现思路

## 1. 项目定位

本项目要实现一个面向课程设计要求的 Pascal-S 到 C 编译器前端与翻译器。目标不是做一个完整 Pascal 编译系统，而是围绕给定 Pascal-S 文法，完成从源程序输入到目标 C 程序输出的整条编译链路，并在编译过程中给出尽量明确的错误信息。

核心产出应包括：

- Pascal-S 源程序的词法分析结果
- 语法分析过程中构造的 AST
- 语义分析与符号表检查结果
- 等价的 C 语言目标代码
- 编译期错误信息与必要的测试样例

本项目的重点是编译期处理，不以运行时检查、优化器或完整解释执行环境为目标。

## 2. 范围边界

实现范围必须以当前工程接口、`testing/open_set` 测试集和现有前端实现为准，不额外扩展到完整 Pascal。

当前明确覆盖的语言结构包括：

- 程序头：`program id`、`program id(idlist)`
- 常量说明：`const`
- 变量说明：`var`
- 基本类型：`integer`、`real`、`boolean`、`char`
- 数组类型：`array[period] of basic_type`
- 过程和函数声明
- 参数传递：值参、`var` 引用参数
- 复合语句：`begin ... end`
- 赋值语句
- 条件语句：`if ... then ... else`
- `while ... do`
- `for ... to ... do` 循环
- 过程调用
- 函数调用
- 零参子程序的 `()` 调用形式
- 零参函数名直接作为表达式使用
- 函数调用结果被忽略的语句形式
- 输入输出：`read(...)`、`write(...)`
- 表达式：关系运算、加法类运算、乘法类运算、`not`、一元正负号
- 布尔字面量：`true`、`false`
- 变量引用与数组下标访问
- 注释：`{...}`、`//...`
- 标识符：大小写不敏感，支持下划线 `_`

当前实现仍未纳入的内容包括：

- `repeat-until`
- 记录、集合、指针、文件类型
- 自定义类型定义
- 复杂运行时库
- 优化型中间代码

因此当前项目更准确地说是“扩展版教学 Pascal 子集”，不是完整 Pascal；是否属于主线能力，应以 `testing/open_set` 是否使用、以及当前 `lexer/parser/semantic` 是否已经落地实现为准。

## 3. 总体技术路线

推荐采用单个编译器程序、内部按阶段分模块实现的方式。整体链路如下：

```text
Pascal-S 源程序
    ↓
词法分析（Flex）
    ↓
语法分析（Bison）
    ↓
AST 构造
    ↓
语义分析 / 符号表 / 作用域检查
    ↓
C 代码生成
    ↓
输出目标 C 程序
```

其中 AST 是整个项目的核心中间表示，后续语义分析和代码生成都应建立在 AST 之上，而不是在语法动作里直接拼接 C 代码。

## 4. 当前工程基础

现有工程已经明确了前端接口和 AST 结构，后续工作应在这一基础上继续推进：

- `code/pascal_s_lexer.l`
  - 使用 Flex 实现词法分析
  - 与 Bison 通过 `yylex / yylval / yylloc` 对接
- `code/pascal_s_parser.y`
  - 使用 Bison 实现 Pascal-S 文法归约
  - 在语义动作中构造 AST
- `code/ast.hpp`、`code/ast.cpp`
  - 定义 AST 节点、构造函数、打印与校验逻辑
- `code/pascal_s_frontend.hpp`
  - 统一前端解析接口
- `code/pascal_s_driver.cpp`
  - 当前用于读取源程序、构造 AST、校验 AST、执行语义分析
  - 默认仅输出语义分析结果，传入 `--dump-ast` 时才打印 AST

因此，项目不是从零开始设计接口，而是在已有前端骨架上补全语义分析、目标代码生成、错误处理完善和测试验证。

## 5. 词法分析要求

词法分析阶段负责把源程序切分成语法分析可直接使用的 token，并维护位置信息。

需要稳定支持的内容包括：

- 关键字识别
- 标识符识别
- 整数、实数、字符常量识别
- 运算符和界符识别
- 空白与注释跳过
- 行列号维护
- 词法错误报告

结合当前实现，应特别注意以下约束：

- 标识符大小写不敏感，统一转小写
- 标识符不再截断到 8 位
- 标识符支持下划线 `_`
- 注释同时支持 `{...}` 和 `//...`
- 词法错误尽量报告后继续扫描
- 未闭合注释和未闭合字符常量必须明确报错

词法分析的输出不是单独保存的 token 文件，而是直接为语法分析器服务。

## 6. 语法分析与 AST 构造要求

语法分析阶段的目标不是只判断“能否通过”，而是要在归约过程中构造结构稳定、可继续处理的 AST。

AST 至少应完整覆盖以下信息：

- 程序头与程序体
- 常量声明、变量声明、类型信息
- 子程序头、参数列表、子程序体
- 语句序列与各种语句节点
- 表达式树
- 变量引用、过程调用、函数调用
- 源代码位置信息

当前 AST 设计已经给出了较清晰的节点体系，后续应严格按该结构使用，不应随意改成“部分节点存字符串、部分节点直接拼接代码”的混合方案。这样可以保证：

- 语义分析阶段有统一输入
- 错误定位可以直接使用节点位置信息
- 代码生成时只需要遍历 AST，不必回看原始 token

## 7. 语义分析要求

语义分析是整个主线中最容易遗漏、但报告和实现都必须交代清楚的一部分。建议将其作为独立模块设计，而不是分散塞进语法动作中。

至少需要覆盖以下检查：

- 标识符是否先声明后使用
- 同一作用域内是否重复声明
- 常量是否被错误赋值
- 数组是否按数组方式使用
- 过程和函数调用的参数个数是否匹配
- 值参和引用参数的使用是否匹配
- 赋值语句左右两侧类型是否兼容
- 条件表达式是否可作为布尔条件使用
- 函数体内函数名赋值是否符合函数返回值语义

语义分析需要建立符号表，并支持作用域嵌套。至少要区分：

- 主程序作用域
- 子程序局部作用域
- 形参符号
- 常量、变量、过程、函数这几类不同符号

建议的实现方式是遍历 AST，分两类工作完成：

1. 建表
2. 检查

如果实现上需要，也可以在一次遍历中同步完成，但文档中必须明确“作用域如何进入和退出、符号如何登记、错误如何记录”。

## 8. C 代码生成要求

目标代码生成要以“语义等价、结构清晰、便于验证”为原则，不追求复杂优化。

建议的映射思路如下：

- 常量声明映射为 C 中可替代的常量定义形式
- 变量声明映射为 C 变量定义
- 数组类型映射为 C 数组
- 过程映射为 `void` 函数
- 函数映射为带返回值的 C 函数
- 复合语句映射为 C 代码块
- `if`、`for`、赋值、调用、表达式按对应语义生成
- `read`、`write` 根据类型映射到合适的输入输出代码

代码生成前要先完成语义分析，不能在语义未确认的前提下直接生成 C，否则后续调试会非常混乱。

代码生成模块至少应解决三个问题：

- 类型如何映射
- 子程序如何映射
- Pascal-S 特有语义如何在 C 中等价表达

其中需要重点处理的点包括：

- 布尔类型与布尔常量表示
- 字符类型与字符常量表示
- 数组下标区间与 C 数组下标差异
- 引用参数在 C 中如何体现
- `read` / `write` 的格式串与参数类型对应

## 9. 错误处理要求

错误处理不能只停留在“报一个错然后退出”，而应尽量做到定位清楚、阶段明确、能继续则继续。

项目中至少区分三类错误：

### 9.1 词法错误

- 非法字符
- 非法标识符
- 未闭合注释
- 未闭合字符常量

### 9.2 语法错误

- 缺失分号、括号、关键字
- 语句结构不完整
- 不符合文法的 token 序列

对于课程设计规模的实现，语法恢复建议只在低风险边界上进行：

- 语句列表以 `;` / `end` 作为主要同步点
- 形参列表、调用实参列表、数组下标列表以右括号或右中括号作为同步点
- `begin ... end` 内部局部损坏时允许跳到 `end` 继续

恢复的目标是“一次编译中尽量多报几条可信错误”，不是带错继续生成目标代码。

### 9.3 语义错误

- 未声明使用
- 重复声明
- 常量赋值
- 类型不匹配
- 参数不匹配

错误信息建议统一包含：

- 错误阶段
- 行号、列号
- 问题描述
- 必要时给出相关标识符名

此外建议补充两条控制规则：

- 词法、语法阶段分别维护错误数量上限，避免错误输入刷屏
- 一旦词法或语法阶段出现错误，驱动层停止进入代码生成阶段

## 10. 测试与验证要求

测试不能只验证“能解析一个样例程序”，而应覆盖主线功能和常见错误场景。

测试内容应至少包括：

- 合法程序样例
- 各类声明组合样例
- 数组、过程、函数样例
- `while`、零参函数、函数语句调用样例
- 表达式优先级样例
- 嵌套语句样例
- 输入输出语句样例
- 词法错误样例
- 语法错误样例
- 语义错误样例

建议按以下层次组织测试：

1. 前端 AST 构造测试
2. 语义分析测试
3. C 代码生成测试
4. 端到端测试

如果条件允许，端到端测试可以采用以下流程：

```text
Pascal-S 源程序
  -> 编译器生成 C
  -> 用 C 编译器编译生成可执行文件
  -> 运行并检查输出
```

当前仓库中，`testing/open_set` 已经可以作为前端阶段的主回归集。该目录下的 `.pas` 文件应全部能够通过词法、语法和语义阶段；若存在同名 `.in` 文件，则表示未来代码生成并执行时还需要配套标准输入。

这样可以同时验证前端、语义和目标代码生成是否一致。

对于错误恢复，还应单独维护 `testing/error_recovery`：

- 语句缺分号恢复
- 形参列表恢复
- 调用实参列表恢复
- 数组下标列表恢复
- 词法错误上限
- 未闭合注释的提前终止

## 11. 推荐模块分工

如果组内需要并行推进，建议按以下主线拆分：

### 11.1 前端组

负责：

- 词法规则维护
- Bison 文法维护
- AST 构造与 AST 校验
- 前端联调

### 11.2 语义组

负责：

- 符号表设计
- 作用域管理
- 语义检查规则
- 语义错误输出

### 11.3 代码生成组

负责：

- 类型映射
- 语句与表达式翻译
- 子程序翻译
- `read/write` 翻译
- 目标 C 文件输出

### 11.4 测试与文档组

负责：

- 样例设计
- 错误用例整理
- 运行结果记录
- 需求分析、总体设计、测试计划、总结等文档撰写

如果人数不足，也至少要保证“前端 / 语义 / 代码生成 / 测试文档”这四条职责被覆盖。

## 12. 开发顺序建议

为了降低返工风险，建议按以下顺序推进：

1. 固定词法与语法接口，确保 AST 能稳定生成
2. 固定 AST 节点语义和子节点布局
3. 完成符号表和语义分析主流程
4. 在语义正确的前提下实现 C 代码生成
5. 补齐错误处理与测试样例
6. 最后整理实验报告和演示材料

这个顺序的关键点是：先把中间表示和语义约束稳定下来，再做目标代码生成。否则后面每改一次语法或 AST，代码生成部分都会跟着返工。

## 13. 最终交付应达到的状态

按照这条路线推进，最终成果应当至少满足：

- 能读取 Pascal-S 源程序
- 能完成词法分析和语法分析
- 能构造并验证 AST
- 能完成基本语义检查
- 能输出可读、可编译的 C 代码
- 能对常见词法、语法、语义错误给出明确提示
- 有覆盖主线功能的测试样例和结果说明
- 文档中的需求、设计、实现、测试彼此一致

这份思路的核心作用是统一项目边界、实现顺序和模块责任。后续无论是继续编码、分配组员任务，还是撰写课程设计文档，都应以这里列出的范围和主线为准。
