# Pascal-S 语义分析实现说明

本文档描述当前工程里语义分析模块的实际落地方式，对应代码文件为：

- `code/semantic/semantic.hpp`
- `code/semantic/semantic.cpp`
- `code/pascal_s_driver.cpp`

实现目标严格对应 `语义分析设计.md` 与 `目标代码生成设计.md`：在 AST 校验通过后，完成建表、作用域管理、类型推导、调用检查，并把代码生成阶段要复用的信息保存在 `SemanticResult` 中。

## 1. 对外接口

`semantic.hpp` 暴露了三个层次的接口。

### 1.1 类型与符号数据结构

- `SemType`
  - 用 `TypeKind` 区分 `Integer / Real / Boolean / Char / String / Array / Void / Invalid`
  - 数组类型通过 `bounds + element_type` 表达
- `Symbol`
  - 统一表示常量、变量、参数、过程、函数
  - 保留 `name / kind / type / by_ref / decl_node / params / c_name`
- `ExprInfo`
  - 记录表达式类型、是否左值、是否允许出现在赋值左侧、直接对应的符号

### 1.2 语义分析结果

`SemanticResult` 除了设计文档中的三个核心映射，还额外保存了两类内部存储：

- `scope_storage`
- `symbol_storage`

这样做的原因是 `resolved_symbols` 和 `ExprInfo.symbol` 里保存的是 `Symbol *`。如果符号只存在于分析器栈帧中，`analyze()` 返回后这些指针会失效，所以结果对象必须显式持有作用域和符号。

### 1.3 分析入口

对外入口只有：

```cpp
class SemanticAnalyzer {
public:
    SemanticResult analyze(const AstNode *root);
};
```

`pascal_s_driver.cpp` 现在在 `ast_validate()` 之后调用它；若 `sem.ok == false`，驱动会打印全部语义错误并返回非零退出码。默认情况下驱动只输出语义分析结果，传入 `--dump-ast` 时才额外打印 AST。

## 2. 实现骨架

`semantic.cpp` 的主体是内部类 `AnalyzerImpl`，`SemanticAnalyzer::analyze()` 只是创建这个实现类并转调 `run()`。

这样写的原因是：

- `semantic.hpp` 只保留稳定接口，不暴露一大批私有辅助函数
- 分析过程中的状态可以集中放在 `AnalyzerImpl` 成员里

当前关键状态有：

- `result_`
  - 当前轮分析要返回的 `SemanticResult`
- `current_scope_`
  - 当前正在分析的作用域
- `current_function_`
  - 当前函数符号，主要给代码生成保留上下文
- `current_function_name_`
  - 当前函数名，用于识别 `f := expr`
- `current_function_type_`
  - 当前函数返回类型，用于给函数结果赋值节点生成 `ExprInfo`
- `subprogram_symbols_`
  - `AST_SUBPROGRAM -> Symbol *` 的映射
- `subprogram_param_specs_`
  - 保存子程序参数的中间规格，进入局部作用域时再转成参数符号
- `used_c_names_`
  - 确保所有 `c_name` 全局唯一

## 3. 作用域与符号表

### 3.1 新作用域创建

`new_scope()` 会创建 `Scope`，设置：

- `parent`
- `owner`
- `depth`

然后把对象放入 `result_.scope_storage`。全局作用域在 `run()` 里创建，子程序作用域在 `analyze_subprogram()` 里创建。

### 3.2 符号登记

统一入口是 `declare_symbol()`，它负责：

1. 检查当前作用域是否重名
2. 创建 `Symbol`
3. 分配 `c_name`
4. 存入 `scope->symbols`
5. 把对象放入 `result_.symbol_storage`

`c_name` 的生成规则在 `make_unique_c_name()` 里实现：

- 常量：`c_`
- 全局变量：`g_`
- 局部变量：`l_`
- 参数：`p_`
- 过程 / 函数：`fn_`

如果同一前缀下重名，会自动追加 `_1`、`_2` 等后缀。

### 3.3 查找规则

- `lookup()`：从 `current_scope_` 开始逐层向外查
- `lookup_current_scope_symbol()`：只查当前层

这两个函数分别用于普通引用解析和“函数结果赋值”判定。

## 4. 总体分析流程

### 4.1 `run()`

`run()` 负责初始化状态、创建全局作用域、调用 `analyze_program()`，最后根据 `result_.errors.empty()` 计算 `result_.ok`。

### 4.2 `analyze_program()`

这里只做一件事：取出 `AST_PROGRAM` 的 `children[1]`，也就是主程序 `AST_BLOCK`，然后交给 `analyze_block()`。

### 4.3 `analyze_block()`

当前块的处理顺序和设计文档一致：

1. `declare_consts()`
2. `declare_vars()`
3. `scan_subprogram_heads()`
4. `analyze_subprograms()`
5. `analyze_stmt()` 处理复合语句

这就是“两阶段”的实际落点：先把当前层声明补齐，再递归检查子程序和语句。

## 5. 声明处理

### 5.1 常量声明

`declare_consts()` 遍历 `AST_CONST_DECL_LIST`，对每个 `AST_CONST_DECL`：

- 取 `children[0]` 作为常量值表达式
- 直接调用 `analyze_expr()` 推导类型
- 用该类型创建 `Const` 符号

这样做的一个好处是：字面量和一元负号常量也会进入 `expr_info`，后续如果代码生成要复用字面量类型，不需要再重复判断。

### 5.2 变量声明

`declare_vars()` 先用 `parse_type()` 解析 `children[1]`，再遍历 `children[0]` 的标识符列表，逐个登记 `Var` 符号。

`parse_type()` 目前支持两类 AST：

- `AST_BASIC_TYPE`
- `AST_ARRAY_TYPE`

对于数组类型，它会读取：

- `children[0]` 的 `AST_PERIOD_LIST`
- `children[1]` 的基类型

并检查每个区间满足 `low <= high`。

### 5.3 子程序头

`scan_subprogram_heads()` 先扫描全部 `AST_SUBPROGRAM` 的头部。

它会先用 `collect_params()` 收集参数规格，再创建过程 / 函数符号：

- 过程返回 `Void`
- 函数返回 `parse_type(children[1])`

参数不会在这一步直接插入局部作用域，只会写入：

- `Symbol.params`
- `subprogram_param_specs_`

这样就满足了“先有完整签名，再分析函数体”的要求。

### 5.4 子程序体

`analyze_subprogram()` 会：

1. 创建局部作用域
2. 设置 `current_function_ / current_function_name_ / current_function_type_`
3. 把参数规格转成 `Param` 符号插入局部作用域
4. 对子程序体 `AST_BLOCK` 再调用一次 `analyze_block()`

这里参数登记用的是 `declare_param()`，本质仍然走 `declare_symbol()`，只是额外把前面算好的 `p_` 前缀 `c_name` 覆盖回去。

## 6. 表达式分析

统一入口是 `analyze_expr()`。它先查 `result_.expr_info` 做缓存；对于普通叶子节点直接分派，对深度很大的单目/双目表达式则走显式栈后序遍历，避免长表达式链造成递归栈溢出。

### 6.1 字面量

- `AST_BOOL_LITERAL` -> `boolean`
- `AST_INT_LITERAL` -> `integer`
- `AST_REAL_LITERAL` -> `real`
- `AST_CHAR_LITERAL` -> `char`
- `AST_STRING_LITERAL` -> `string`

它们都返回：

- `is_lvalue = false`
- `is_assignable = false`

### 6.2 变量引用

`analyze_var_ref()` 是表达式分析里最核心的一段。

处理顺序是：

1. `lookup(node->text)` 解析名字
2. 记录到 `result_.resolved_symbols[node]`
3. 拒绝把 `Procedure` 当表达式
4. 拒绝把 `Function` 名字直接当变量
5. 若无下标：
   - 常量可读不可写
   - 普通变量 / 参数可读
   - 零参函数名可直接作为表达式值使用
   - 整个数组返回 `Array` 类型，但 `is_assignable = false`
6. 若有下标：
   - 原类型必须是数组
   - 下标个数必须等于维数
   - 每个下标表达式都必须是 `integer`
   - 返回元素类型

这一步已经把“整个数组不能直接参与赋值 / read / write”编码进 `ExprInfo` 里了，语句分析只需要基于 `ExprInfo` 再做场景判断。

### 6.3 调用表达式

`analyze_call_expr()` 负责函数调用：

1. 解析名字
2. 要求符号种类必须是 `Function`
3. 记录 `resolved_symbols[node]`
4. 调用 `check_call_arguments()`
5. 返回函数返回类型

### 6.4 一元与二元表达式

- `analyze_unary_expr()`
  - `+` 只接受数值型
  - `-` 只接受数值型
  - `not` 接受 `boolean` 或 `integer`
- `analyze_binary_expr()`
  - `+ - *`：数值型，按 `integer/real` 提升
  - `/`：数值型，结果固定 `real`
  - `div mod`：两侧必须 `integer`
  - `and or`：两侧必须 `boolean`
  - 关系运算：允许数值比较、`char` 比较、`boolean` 比较，结果统一为 `boolean`

关系运算的可比较性被单独抽成了 `comparable_types()`。

## 7. 语句分析

### 7.1 赋值语句

`analyze_assign_stmt()` 先处理左侧，再处理右侧。

特殊点在函数返回值赋值：

- 由 `is_current_function_result_ref()` 识别
- 条件是：
  - 当前处在函数体内
  - 左值节点是 `AST_VAR_REF`
  - 名字等于当前函数名
  - 没有下标
  - 当前局部作用域内没有同名普通符号

一旦命中：

- 左值类型直接取 `current_function_type_`
- 节点加入 `result_.function_result_refs`
- 代码生成阶段就能把它翻成 `__result = ...`

普通赋值检查则包括：

- 左侧必须可赋值
- 整个数组不能做赋值目标
- `assignment_compatible(lhs, rhs)` 必须成立

### 7.2 子程序调用语句

`analyze_call_stmt()` 与函数调用复用同一套参数检查。当前实现允许：

- 过程调用语句
- 函数调用结果被忽略的语句

### 7.3 `if`

`analyze_if_stmt()` 先分析条件表达式，再要求条件类型必须是 `boolean`，最后递归检查 then / else。

### 7.4 `for`

`analyze_for_stmt()` 直接读取 `AST_FOR_STMT.text` 中保存的循环变量名。

它会检查：

- 名字是否可解析
- 符号种类是否为 `Var / Param`
- 类型是否为 `integer`
- 起始表达式是否为 `integer`
- 终止表达式是否为 `integer`

同时，循环变量对应的符号也会被记录进 `resolved_symbols[node]`，这样后续代码生成可以直接拿到 `c_name`。

### 7.5 `while`

`analyze_while_stmt()` 会先检查条件是否为 `boolean`，再递归分析循环体。

### 7.6 `break`

`analyze_break_stmt()` 要求 `break` 只能出现在循环体内。

### 7.7 `read` / `write`

- `analyze_read_stmt()`
  - 参数必须是可赋值左值
  - 整个数组直接报错
  - 类型只允许 `integer / real / boolean / char`
- `analyze_write_stmt()`
  - 整个数组直接报错
  - 输出类型允许 `integer / real / boolean / char / string`

## 8. 参数匹配

`check_call_arguments()` 统一处理过程和函数的参数检查。

逻辑是：

1. 先递归分析所有实参表达式
2. 检查实参数量
3. 按位置逐个检查

规则分两类：

- 值参数
  - 用 `assignment_compatible()` 判断
- `var` 参数
  - 实参必须是可赋值左值
  - 类型必须 `same_type()`

这里的报错位置绑定在调用点，而不是形参声明点，方便直接定位到有问题的调用。

## 9. 语义结果如何服务代码生成

当前实现已经把代码生成需要的几类信息都准备好了：

- `resolved_symbols`
  - 变量引用、调用节点、`for` 节点都能回到具体符号
- `expr_info`
  - 所有表达式节点都能直接拿到类型和左值属性
- `function_result_refs`
  - 能识别 Pascal 函数体里的“函数名赋值”
- `Symbol.c_name`
  - 代码生成阶段不必自己再做命名决策

换句话说，后续 `codegen.cpp` 不需要再重新做名字解析和类型推导，只需要消费这些结果。

## 10. 驱动程序集成

`pascal_s_driver.cpp` 的执行顺序现在是：

1. `parse_pascal_file()` / `parse_pascal_stream()`
2. `ast_validate()`
3. `SemanticAnalyzer::analyze()`
4. 若失败，`print_semantic_errors()`
5. 若成功，输出 `semantic analysis: ok`
6. 若命令行带 `--dump-ast`，则先打印 AST

这保证了：

- 词法/语法错误先失败
- AST 结构错误单独失败
- 语义错误集中输出
