# Pascal-S 语义分析设计

## 1. 目标

语义分析阶段位于 AST 构造之后、C 代码生成之前。它的职责不是重新解析源程序，而是基于 AST 完成以下工作：

- 建立符号表
- 管理作用域
- 推导表达式类型
- 检查声明与使用关系
- 检查调用与参数匹配关系
- 检查赋值、条件、循环、输入输出等语义约束
- 为后续代码生成提供稳定的语义信息

当前工程中，词法、语法和 AST 已完成，因此语义分析的输入应固定为 `AstNode *root`。

## 2. 输入与输出

### 2.1 输入

- `parse_pascal_file` 或 `parse_pascal_stream` 返回的 AST 根节点
- `ast_validate` 已通过的结构化 AST

### 2.2 输出

语义分析输出不应只是“通过 / 失败”，而应包含：

- 语义错误列表
- AST 节点到符号的解析结果
- AST 表达式节点的类型信息
- 供代码生成复用的命名和类型映射信息

建议定义统一的结果对象：

```cpp
struct SemanticResult {
    bool ok;
    std::vector<SemanticError> errors;
    std::unordered_map<const AstNode *, ExprInfo> expr_info;
    std::unordered_map<const AstNode *, const Symbol *> resolved_symbols;
    std::unordered_set<const AstNode *> function_result_refs;
    std::vector<std::unique_ptr<Scope> > scope_storage;
    std::vector<std::unique_ptr<Symbol> > symbol_storage;
};
```

## 3. 模块划分

建议新增两个文件：

- `code/semantic/semantic.hpp`
- `code/semantic/semantic.cpp`

其中主要包含：

- 类型系统定义
- 符号表和作用域结构
- 语义错误结构
- 语义分析主类 `SemanticAnalyzer`

推荐接口：

```cpp
class SemanticAnalyzer {
public:
    SemanticResult analyze(const AstNode *root);
};
```

## 4. 类型系统设计

语义分析必须先把“Pascal-S 的类型”独立建模出来，不能只依赖 AST 节点类型名字符串。

建议定义：

```cpp
enum class TypeKind {
    Integer,
    Real,
    Boolean,
    Char,
    String,
    Array,
    Void,
    Invalid
};

struct ArrayBound {
    int low;
    int high;
};

struct SemType {
    TypeKind kind;
    std::vector<ArrayBound> bounds;
    std::shared_ptr<SemType> element_type;
};
```

说明：

- `Integer`、`Real`、`Boolean`、`Char`、`String` 对应基本类型
- `Array` 保存每一维的上下界和元素类型
- `Void` 用于过程
- `Invalid` 用于错误恢复，避免一次出错导致整棵树无法继续分析

建议提供辅助函数：

- `bool is_numeric(const SemType &type)`
- `bool is_scalar(const SemType &type)`
- `bool same_type(const SemType &a, const SemType &b)`
- `bool assignment_compatible(const SemType &lhs, const SemType &rhs)`
- `std::string type_to_string(const SemType &type)`

其中赋值兼容规则建议为：

- 相同类型可赋值
- `integer` 可赋给 `real`
- 其余情况一律视为不兼容

## 5. 符号表设计

### 5.1 符号种类

建议定义：

```cpp
enum class SymbolKind {
    Const,
    Var,
    Param,
    Procedure,
    Function
};
```

### 5.2 参数信息

```cpp
struct ParamInfo {
    std::string name;
    SemType type;
    bool by_ref;
    std::string c_name;
};
```

### 5.3 符号信息

```cpp
struct Symbol {
    std::string name;
    SymbolKind kind;
    SemType type;
    bool by_ref;
    const AstNode *decl_node;
    std::vector<ParamInfo> params;
    std::string c_name;
};
```

说明：

- 常量、变量、参数都使用 `type`
- 过程符号的 `type` 为 `Void`
- 函数符号的 `type` 为返回类型
- `params` 仅对过程和函数有效
- `c_name` 在语义阶段生成，供代码生成阶段复用

### 5.4 作用域结构

```cpp
struct Scope {
    Scope *parent;
    std::unordered_map<std::string, Symbol *> symbols;
};
```

至少需要支持：

- 全局作用域
- 子程序局部作用域

查找规则采用“当前作用域优先，逐层向外查找”。

## 6. AST 附加语义信息

为了避免代码生成阶段再次推导表达式类型，建议在语义分析阶段直接记录附加信息。

```cpp
struct ExprInfo {
    SemType type;
    bool is_lvalue;
    bool is_assignable;
    const Symbol *symbol;
};
```

含义：

- `type`：该表达式最终类型
- `is_lvalue`：是否可作为左值引用
- `is_assignable`：是否可出现在赋值左侧
- `symbol`：若该表达式直接对应某个标识符，记录解析到的符号

需要记录的节点包括：

- `AST_VAR_REF`
- `AST_CALL_EXPR`
- `AST_BINARY_EXPR`
- `AST_UNARY_EXPR`
- 字面量节点

## 7. 总体分析流程

建议采用“两阶段分析”。

### 7.1 第一阶段：登记声明

目标是把所有声明信息放入正确作用域，尤其是子程序签名。

主程序块处理顺序建议为：

1. 创建全局作用域
2. 处理常量声明
3. 处理变量声明
4. 扫描所有子程序头，先登记过程 / 函数符号及参数签名
5. 再进入每个子程序体做局部建表和检查

这样可以支持子程序之间的调用检查，也便于代码生成提前拿到完整函数签名。

### 7.2 第二阶段：语义检查

在声明完整后，对语句和表达式进行类型推导和一致性检查。

检查范围包括：

- 标识符解析
- 左值合法性
- 调用合法性
- 参数匹配
- 表达式类型
- 赋值兼容
- 条件和循环语义
- 数组使用规则

## 8. 各类声明的处理逻辑

### 8.1 常量声明

对应节点：`AST_CONST_DECL`

处理逻辑：

1. 读取常量名
2. 分析右侧常量值节点
3. 推导出常量类型
4. 在当前作用域中插入 `Const` 符号
5. 若同一作用域重名，报重复声明错误

注意：

- 当前常量值可以是整数、实数、字符、字符串、布尔字面量，或一元正负号作用于数字字面量

### 8.2 变量声明

对应节点：`AST_VAR_DECL`

处理逻辑：

1. 解析 `children[1]` 得到类型
2. 遍历 `children[0]` 中的每个标识符
3. 为每个标识符插入 `Var` 符号
4. 检查同一作用域内是否重复声明

### 8.3 过程 / 函数声明

对应节点：

- `AST_PROCEDURE_HEAD`
- `AST_FUNCTION_HEAD`
- `AST_SUBPROGRAM`

处理顺序建议为：

1. 先扫描头部，创建过程 / 函数符号
2. 收集参数列表，写入 `params`
3. 若为函数，记录返回类型
4. 进入子程序局部作用域
5. 把参数作为局部符号插入
6. 处理子程序体中的常量、变量和语句

对函数需要额外记录：

- 当前所在函数符号 `current_function`

它用于识别“函数体内给函数名赋值”这一 Pascal-S 返回值规则。

## 9. 表达式分析规则

表达式分析的统一入口建议为：

```cpp
ExprInfo analyze_expr(const AstNode *node);
```

### 9.1 字面量

- `AST_BOOL_LITERAL` -> `boolean`
- `AST_INT_LITERAL` -> `integer`
- `AST_REAL_LITERAL` -> `real`
- `AST_CHAR_LITERAL` -> `char`
- `AST_STRING_LITERAL` -> `string`

这些表达式都不是左值。

### 9.2 变量引用 `AST_VAR_REF`

处理逻辑：

1. 根据 `text` 在作用域链上查找符号
2. 若未找到，报“未声明标识符”
3. 若找到的是过程符号，报错
4. 判断是否带下标
5. 若带下标：
   - 原类型必须为数组
   - 下标个数必须与维数一致
   - 每个下标表达式必须为 `integer`
   - 完整下标后表达式类型变为元素类型
6. 若不带下标：
   - 普通变量和参数可作为值使用
   - 零参函数名可直接作为表达式值使用
   - 数组变量作为整体值时暂不允许参与普通运算

左值规则建议为：

- 普通变量可以作为左值
- 值参数和引用参数都可以作为左值
- 常量不能作为左值
- 完整数组元素引用可以作为左值

### 9.3 函数调用 `AST_CALL_EXPR`

处理逻辑：

1. 名称必须能解析到 `Function`
2. 检查实参数量
3. 按参数列表逐一检查类型和传参方式
4. 返回类型为函数声明中的返回类型

### 9.4 一元表达式 `AST_UNARY_EXPR`

- `+`
  - 操作数必须为数值型
  - 结果类型与操作数一致
- `-`
  - 操作数必须为数值型
  - 结果类型与操作数一致
- `not`
  - 操作数必须为 `boolean` 或 `integer`
  - 结果类型与操作数一致

### 9.5 二元表达式 `AST_BINARY_EXPR`

#### 算术运算

- `+` `-` `*`
  - 两侧都必须是数值型
  - 若任一侧为 `real`，结果为 `real`
  - 否则结果为 `integer`

#### 实数除法

- `/`
  - 两侧都必须是数值型
  - 结果固定为 `real`

#### 整数运算

- `div` `mod`
  - 两侧必须为 `integer`
  - 结果为 `integer`

#### 逻辑运算

- `and` `or`
  - 两侧必须为 `boolean`
  - 结果为 `boolean`

#### 关系运算

- `=` `<>` `<` `<=` `>` `>=`
  - 两侧必须可比较
  - 建议先支持：
    - 数值型之间比较
    - `char` 与 `char`
    - `boolean` 与 `boolean`
  - 结果为 `boolean`

## 10. 语句分析规则

### 10.1 赋值语句 `AST_ASSIGN_STMT`

检查顺序建议为：

1. 分析左侧 `AST_VAR_REF`
2. 分析右侧表达式
3. 左侧必须 `is_assignable`
4. 右侧类型必须能赋给左侧类型

函数返回值赋值需要特殊处理：

- 若当前在函数体内
- 且赋值左侧名称等于当前函数名
- 且没有数组下标

则将该左值识别为“函数结果赋值”，而不是普通变量赋值。

建议做法：

- 不把“函数名返回值变量”显式插入普通符号表
- 在分析赋值语句时单独识别
- 把对应左值节点记录到 `function_result_refs`

这样代码生成阶段可直接把它翻译为 `__result = expr;`

### 10.2 过程调用语句 `AST_CALL_STMT`

检查逻辑：

1. 名称必须解析到 `Procedure` 或 `Function`
2. 检查实参数量
3. 按位置匹配实参和形参
4. 对 `var` 参数要求实参必须是可赋值左值，且类型严格一致

说明：

- 为兼容测试集，函数调用结果允许在语句位置被忽略
- 若语句位置写的是零参函数名，语法阶段同样会构造调用语句节点

### 10.3 条件语句 `AST_IF_STMT`

- 条件表达式必须为 `boolean`
- `then` 与 `else` 分支递归检查

### 10.4 `while` 语句 `AST_WHILE_STMT`

- 条件表达式必须为 `boolean`
- 循环体递归检查

### 10.5 `for` 语句 `AST_FOR_STMT`

建议检查：

- 循环变量必须已声明
- 循环变量必须是可赋值整数变量
- 起始表达式必须为 `integer`
- 终止表达式必须为 `integer`
- 循环体递归检查

### 10.6 `break` 语句 `AST_BREAK_STMT`

- 只能出现在 `while` 或 `for` 循环内部

### 10.7 `read` 语句 `AST_READ_STMT`

建议限制：

- 每个参数必须是可赋值左值
- 类型仅允许 `integer`、`real`、`char`、`boolean`
- 不允许把整个数组作为 `read` 目标

### 10.8 `write` 语句 `AST_WRITE_STMT`

建议限制：

- 每个参数必须是可计算表达式
- 类型允许 `integer`、`real`、`char`、`boolean`、`string`
- 暂不支持直接输出整个数组

## 11. 参数匹配规则

参数检查建议统一封装：

```cpp
bool check_call_arguments(const Symbol &callee,
                          const AstNode *call_node,
                          const AstNode *arg_list_node);
```

具体规则如下：

- 实参数量必须等于形参数量
- 值参数：
  - 要求表达式类型兼容
  - 可接受 `integer -> real`
- 引用参数：
  - 实参必须是可赋值左值
  - 类型必须严格一致
  - 不允许字面量、临时表达式、函数调用结果作为实参

## 12. 错误处理策略

语义分析不应“遇到第一个错就退出”，而应尽量继续分析并累计错误。

建议定义：

```cpp
struct SemanticError {
    AstLocation loc;
    std::string message;
};
```

错误报告建议统一格式：

```text
[语义错误] 行:列 - 描述
```

典型错误包括：

- 重复声明
- 未声明标识符
- 常量赋值
- 非数组使用下标
- 数组下标个数不匹配
- 数组下标类型错误
- 过程 / 函数使用位置错误
- 参数个数不匹配
- `var` 参数要求左值
- 类型不匹配
- 条件表达式不是布尔类型
- 非法函数返回值赋值

恢复策略建议：

- 出错节点返回 `Invalid` 类型
- 后续检查遇到 `Invalid` 时尽量不重复报派生错误
- 语法恢复产生的空语句、空参数列表、空实参列表应视为合法空结构
- 若恢复导致局部子节点缺失，语义阶段优先退化为 `Invalid`，不应因 `assert` 或越界访问崩溃

## 13. 与代码生成的接口约定

代码生成阶段不应重新做符号查找和类型推导，而应直接消费语义分析结果。

语义分析至少要向代码生成暴露：

- 每个标识符引用对应哪个符号
- 每个表达式节点的类型
- 每个符号的 C 侧名称 `c_name`
- 哪些赋值左值是函数返回值引用

这样可以保证：

- 代码生成逻辑简单
- 不会因为重复推导出现前后不一致
- 后续改语义规则时只需改一处

## 14. 实现顺序建议

建议按以下顺序完成语义分析模块：

1. 先实现 `SemType`、`Symbol`、`Scope`
2. 实现声明登记逻辑
3. 实现标识符查找和变量引用检查
4. 实现表达式类型推导
5. 实现语句检查
6. 实现调用和参数匹配
7. 接入驱动程序，输出语义错误
8. 最后为代码生成补齐 `c_name` 和 AST 注解信息

## 15. 当前文法下的注意事项

- 当前词法和语法已支持布尔字面量 `true`、`false`
- 当前词法和语法已支持字符串字面量
- 当前词法支持 `//` 行注释和带下划线的标识符
- 当前语法支持 `while`
- 当前语法支持 `break`
- 当前语法支持零参子程序的 `()` 调用形式
- 当前语法兼容零参函数名直接作为表达式值使用
- 当前子程序体内部不再声明嵌套子程序，但作用域实现建议保留通用能力
- 当前数组元素类型只支持基本类型
- 当前 `for` 仅支持 `to`，不支持 `downto`

因此语义分析设计应严格围绕当前 AST 规则落地，不要默认扩展成完整 Pascal。
