# 开放集测试 93 修复记录

## 1. 现象

- 用例：开放集 93（递归 Simpson 积分计算 `|x|`、`x^2`、`sqrt(x)`、`exp(x)`、`ln(x)`、`log_a N`、`a^x`）。
- 提交后头歌返回的数值与期望偏差较大（例如首列出现 `0.202296` 这类值），但本地 macOS / clang 编译生成的 C 又能跑出正确结果。
- 排除：浮点格式（`%f`）、`real` 改 `double`、`@` 替换、stdout flush 等都不是主因——同一份生成 C 在 macOS clang 与 Debian 9 GCC 下输出不同，必然是平台相关的 C 行为差异。

## 2. 根因

`code/codegen/codegen.cpp` 在重构调用实参时采用了"逗号表达式 + 临时槽"的方案，把每个调用点的实参先写入 `__call_tmp_*[i]`，再以这些槽作为函数实参，目的是固定实参求值顺序：

```c
(slot1 = arg1_expr, slot2 = arg2_expr, fn(slot1, slot2))
```

修复前，所有槽数组以 **模块级 `static` 数组** 形式声明：

```c
static int   __call_tmp_i[N];
static float __call_tmp_r[M];
static int  *__call_tmp_pi[K];
...
```

且槽下标由一个全局计数器 `call_temp_usage_` 单调递增分配，不同调用点的下标互不相同。

这种方案在 93 上崩塌，触发点是 `fn_asr5` 中的递归二分：

```pascal
asr5 := asr5(a, c, eps/2, L, flag) + asr5(c, b, eps/2, R, flag);
```

对应生成的 C 代码（修复前）：

```c
__result =
  (__call_tmp_i[3]=p_flag_1, __call_tmp_r[14]=l_l,  __call_tmp_r[15]=p_eps/2,
   __call_tmp_r[16]=l_c_2,   __call_tmp_r[17]=p_a_2,
   fn_asr5(__call_tmp_r[17], __call_tmp_r[16], __call_tmp_r[15],
           __call_tmp_r[14], __call_tmp_i[3]))
+ (__call_tmp_i[4]=p_flag_1, __call_tmp_r[18]=l_r,  __call_tmp_r[19]=p_eps/2,
   __call_tmp_r[20]=p_b_1,   __call_tmp_r[21]=l_c_2,
   fn_asr5(__call_tmp_r[21], __call_tmp_r[20], __call_tmp_r[19],
           __call_tmp_r[18], __call_tmp_i[4]));
```

左右两侧的下标互不冲突（`r[14..17]/i[3]` vs `r[18..21]/i[4]`），看起来"安全"，但有两个 C 规则同时生效：

1. `+` 两个操作数之间 **没有 sequence point**，求值顺序未指定，且可以交错。逗号表达式只在内部强制了顺序。
2. `__call_tmp_*` 是 **模块级 static 数组，不可重入**。`fn_asr5` 递归进入时，再次执行同一段代码，会重新写入 **同一批** `r[14..21]/i[3..4]`。

可能的合法时序之一：
1. 编译器先把左右两侧所有槽都写完（`i[3]`、`r[14..17]`、`i[4]`、`r[18..21]`）。
2. 调用左侧 `fn_asr5(...)`。其内部递归再次进入相同代码，**覆盖** `r[18..21]` 等槽。
3. 再调用右侧 `fn_asr5(...)`——这次它的实参槽已被深层递归写花，传入的是错误的值。

macOS clang 选择的求值/调度策略恰好把"准备 → 调用 → 准备 → 调用"串行化了，所以正确；Debian 9 的 GCC 6.3 落到坏顺序上，于是输出错误。同一份 C，在两台机器上行为不同，正是 *未指定行为 + 非重入全局状态* 的典型征兆。

> 顺带：`__call_tmp_r` 用的是 `float`（约 7 位有效数字），但 93 里 `eps = 1e-8`。这是潜在隐患，但与"同一份 C 在两个平台上输出差距很大"现象不一致——纯精度问题不会在 clang 下恰好正确，所以主因不是 float/double。

## 3. 修复

把 `__call_tmp_*` 从 **模块级 `static` 数组** 改为 **每个函数体内部的 auto 局部数组**，让它随调用栈天然可重入。

- `code/codegen/codegen.cpp`
  - 删除 `emit_program` 里 `plan_call_temps(node)` 和 `emit_call_temp_decls()` 的全局调用。
  - `emit_call_temp_decls` 改名为 `emit_local_call_temp_decls`，发射的是局部 `int __call_tmp_i[N];` / `float __call_tmp_r[M];` 等（去掉 `static`），并在末尾把 `call_temp_usage_` 复位。
  - `emit_subprogram`：在发射完 `__result` 与本地 `const/var` 声明后，重置 `call_temp_capacity_ / call_temp_usage_`，对当前子程序的 `compound_stmt` 跑 `plan_call_temps`，按本函数实际容量发射一批局部 `__call_tmp_*` 数组，再发射语句体。
  - `emit_main`：同上，在 `main` 体开头按 main 自己的容量发射局部数组。
- `code/codegen/codegen.hpp`：`emit_call_temp_decls` 重命名为 `emit_local_call_temp_decls`。

槽下标仍在同一函数内单调递增；不同子程序之间的下标互不影响；每次进入函数都是新的栈帧、新的数组，因此递归调用 **不再共享** 上一层的槽。

修复后 `fn_asr5` 生成代码片段：

```c
float fn_asr5(float p_a_2, float p_b_1, float p_eps, float p_aa, int p_flag_1) {
    float __result = 0.0;
    float l_c_2;
    float l_l;
    float l_r;
    int __call_tmp_i[4];
    float __call_tmp_r[13];

    l_c_2 = p_a_2 + (p_b_1 - p_a_2) / 2;
    l_l = (__call_tmp_i[0]=p_flag_1, __call_tmp_r[0]=l_c_2, __call_tmp_r[1]=p_a_2,
           fn_simpson(__call_tmp_r[1], __call_tmp_r[0], __call_tmp_i[0]));
    ...
    __result = (__call_tmp_i[2]=p_flag_1, __call_tmp_r[5]=l_l,  __call_tmp_r[6]=p_eps/2,
                __call_tmp_r[7]=l_c_2,   __call_tmp_r[8]=p_a_2,
                fn_asr5(__call_tmp_r[8], __call_tmp_r[7], __call_tmp_r[6],
                        __call_tmp_r[5], __call_tmp_i[2]))
              + (__call_tmp_i[3]=p_flag_1, __call_tmp_r[9]=l_r,  __call_tmp_r[10]=p_eps/2,
                 __call_tmp_r[11]=p_b_1,   __call_tmp_r[12]=l_c_2,
                 fn_asr5(__call_tmp_r[12], __call_tmp_r[11], __call_tmp_r[10],
                         __call_tmp_r[9],  __call_tmp_i[3]));
    return __result;
}
```

数组都是 `auto`、随栈帧产生，递归层互不污染。

## 4. 构建与验证

### 4.1 本机构建（macOS）

```bash
cd code/build
cmake --build .
```

### 4.2 Debian 9 二进制（Docker）

宿主机 macOS / Apple Silicon，使用 `linux/amd64` 平台拉起 `debian:9`，从 Kitware 拉一个较新的 `cmake` 即可（仓库自带的 `cmake` 3.7 不够 `cmake_minimum_required(VERSION 3.16)`）：

```bash
docker run --rm --platform linux/amd64 \
  -v /Users/yuanweitu/Desktop/college/编译课设/code:/work \
  debian:9 bash -c '
    cat > /etc/apt/sources.list <<EOF
deb http://archive.debian.org/debian stretch main
deb http://archive.debian.org/debian-security stretch/updates main
EOF
    echo "Acquire::Check-Valid-Until \"false\";" > /etc/apt/apt.conf.d/99no
    apt-get -o Acquire::AllowInsecureRepositories=true update -qq
    apt-get install -y --no-install-recommends --allow-unauthenticated \
        build-essential flex bison curl ca-certificates >/dev/null
    cd /tmp
    curl -fsSL -o cmake.tar.gz \
      https://github.com/Kitware/CMake/releases/download/v3.27.7/cmake-3.27.7-linux-x86_64.tar.gz
    tar -xzf cmake.tar.gz
    export PATH=/tmp/cmake-3.27.7-linux-x86_64/bin:$PATH
    cd /work
    rm -rf build_docker_debian9 && mkdir build_docker_debian9 && cd build_docker_debian9
    cmake .. -DCMAKE_BUILD_TYPE=Release
    cmake --build . -j$(nproc)
    cp bin/pascc       /work/pascc.debian9
    cp bin/pascc_dummy /work/pascc_dummy.debian9
'
```

产物：

- `code/pascc.debian9`：ELF64 LSB, x86-64, dynamically linked, glibc 2.6.32+。
- `code/pascc_dummy.debian9`：同上。

### 4.3 端到端验证

`test93.pas` ← `文档/93.md` 中的源码（把 `@` 还原为 `*`）。在同一份 `debian:9` 容器中：

```bash
./pascc.debian9 -i test93.pas
gcc -O2 -w test93.c -o test93.bin
printf "1.5\n2.0\n0.5\n3.0\n" | ./test93.bin
```

输出（Debian 9 / GCC 6.3）：

```
1.500000 2.250000 1.224745 3.580747 0.405465 1.709511 1.797685
0.500000 0.250000 0.707107 1.317237 -0.693147 -1.584962 0.156483
```

与 macOS / clang 上跑同一份生成 C 的输出 **逐字节一致**——确认 Debian 9 不再出现错误偏差。

## 5. 影响面

- 修改局限在 codegen 这一层，不动语义、词法、语法。
- 之前已经修过的用例（47、57、62、35 等）生成的 C 代码形状不变，唯一区别是数组从 `static int __call_tmp_i[N];` 这种模块级声明，挪到了每个函数体顶端的 `int __call_tmp_i[N];`。
- 栈占用增加：每个调用了别的函数的函数额外多几十到上百字节的栈，可忽略。
- 不影响 `-Wall -Wextra -pedantic` 通过性（C99 局部数组合法）。
